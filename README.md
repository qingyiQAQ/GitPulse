# GitPulse

> 自动监控 GitHub 上最热门的开源项目，判断其是否与互联网 / 编程 / AI 相关，相关则生成摘要并推送给你。

一个以「真实业务闭环」为载体的 **AI Agent 学习项目**，最终目标是落地为**企业级 AI Agent**。使用 **Go** 开发。

## 1. 项目愿景与定位

### 1.1 愿景

**GitPulse** 的使命用一句话概括：

> 让用户每天用最少的时间，掌握 GitHub 上最值得关注的开源趋势。

它解决的是一个真实且高频的痛点：**信息过载**。GitHub 每天涌现大量新项目，手动刷 Trending 既费时又低效，而且大部分项目与个人关注领域无关。

### 1.2 定位：学习项目 → 企业级项目

GitPulse 是双目标的：

| 维度 | 目标 | 说明 |
|---|---|---|
| **业务目标** | 真正跑通「监控 → 判断 → 摘要 → 推送」闭环 | 解决真实问题，而非玩具 Demo |
| **学习目标** | 用真实项目承载 `learn/learn.md` 的五阶段路线 | 每阶段的知识点都落在一个可运行的模块上 |

**企业级与个人项目的本质差异**（贯穿整个项目的核心原则）：

> **稳定、可控、可观测、可治理。**

个人项目「能跑就行」，企业级项目要求：输出可解析、行为可追溯、异常可降级、成本可归因、权限有边界、评估可量化。

这条原则会反哺到每个模块的设计决策中——当你在「简单实现」和「工程化实现」之间犹豫时，优先选择后者，因为那才是本项目要练习的能力。

## 2. 核心任务定义

把课题拆成一条清晰的 **Pipeline**，每一步的输入输出、成功标准、失败策略都明确下来。

```
输入              处理                                  输出
─────────────────────────────────────────────────────────────────
GitHub 热门数据 ──▶ [1] 采集     ──▶ 结构化项目列表（含去重）
                      │
                      ▼
                   [2] 相关性判断 ──▶ 二分类 + 置信度 + 理由
                      │
                      ▼
                   [3] 摘要生成   ──▶ 结构化摘要（一句话 + 要点）
                      │
                      ▼
                   [4] 推送       ──▶ 多渠道消息（微信/邮件/钉钉…）
```

### 2.1 四步任务拆解

| 步骤 | 名称 | 核心动作 | 关键约束 |
|---|---|---|---|
| 1 | **采集** | 拉取 GitHub Trending / Search，抓取项目元数据 | 限流、幂等去重、增量 |
| 2 | **相关性判断** | LLM 判断是否与「互联网 / 编程 / AI」相关 | 结构化输出、置信度阈值、可解释 |
| 3 | **摘要生成** | 对相关项目生成精炼摘要 | 结构化、长度受控、可溯源 |
| 4 | **推送** | 将结果推送给用户 | 多渠道适配、失败重试、去重 |

### 2.2 成功标准（定义「什么叫做好了」）

- **准确**：相关性判断的准确率可被量化评估（有 Eval 数据集，而非「感觉挺准」）。
- **稳定**：任一步骤失败都不影响整体（降级而非崩溃），可重试、可告警。
- **可观测**：每一次「思考—行动—观察」都有轨迹，能回答「它为什么推了这个」。
- **可控成本**：Token 消耗按步骤归因，能用 mini 模型的地方不用大模型。
- **可治理**：Prompt 有版本、Agent 有身份、操作有审计、高风险动作有人工兜底。

### 3.2 分层职责

| 层 | 职责 | 对应学习阶段 | Go 实现位置 |
|---|---|---|---|
| **调度层** | 定时触发任务、管理运行周期 | 阶段五 | `cmd/`（入口）+ cron |
| **编排层** | Agent 循环、任务编排、异常重试 | 阶段一、三 | `internal/agent/` |
| **工具层** | 封装外部系统（GitHub、推送）为可调用工具 | 阶段一、四 | `internal/tools/` |
| **记忆层** | 去重、用户偏好、会话上下文 | 阶段一、三 | `internal/memory/` |
| **模型层** | LLM 调用、结构化输出、Prompt 管理 | 阶段一 | `internal/model/` + `internal/prompt/` |
| **知识层** | RAG 检索、历史摘要沉淀 | 阶段二 | `internal/rag/`（后续） |
| **基础设施层** | 可观测、评估、治理、部署 | 阶段五 | `internal/observability/` 等（后续） |

### 3.3 架构演进策略

遵循 `learn/learn.md` 阶段三的核心建议：**不要为了「高级」而上多 Agent**。

- **MVP（阶段一）**：单 Agent + 确定性链，把四步 Pipeline 跑通。
- **进阶（阶段三）**：当步骤之间出现分支（如低置信度需人工复核）时，引入 DAG 编排。
- **生产（阶段五）**：按需引入事件驱动并发、分层路由，而非堆砌复杂度。

## 4. 核心组件设计

### 4.1 Agent 核心循环

所有复杂架构的底层单元都是这条循环：

```
PLAN     ──▶ 决定下一步做什么（抓取？分类？摘要？推送？）
   │
   ▼
ACT      ──▶ 调用工具（GitHub API / LLM 结构化输出 / 推送客户端）
   │
   ▼
OBSERVE  ──▶ 读取工具返回，校验结果，更新状态，进入下一轮 PLAN
```

对应 Go 中的 `internal/agent/agent.go` 的 `Agent.Step`。**工程化要点**：循环的每一步都落一条 trace（阶段五可观测性），工具调用失败有重试与熔断，输出解析失败有降级策略。

### 4.2 工具层（Tools）

每个外部系统封装为一个「工具」，具备清晰的描述与参数 Schema（阶段一 Function Calling）。Go 中以 `Tool` 接口统一（`internal/tools/tool.go`）：

| 工具 | 名称 | 说明 |
|---|---|---|
| `GitHubTool` | `github` | 抓取 Trending / 项目详情 |
| `JudgeTool` | `judge_relevance` | LLM 判断相关性，输出 `RelevanceVerdict` |
| `SummarizeTool` | `summarize_repo` | LLM 生成摘要，输出 `Summary` |
| `PushTool` | `push` | 多渠道推送，内部用 Adapter 解耦 |

**设计原则**：工具是「薄封装」，业务逻辑（去重、阈值、降级）放在编排层（`internal/agent`），而非塞进工具内部——这样工具可复用、可替换、可测试。

### 4.3 结构化输出（Structured Output）

这是企业级的第一个硬要求：**下游系统必须可解析、可校验**，而非「大概意思对」。Go 中用 `struct + json tag` 承担 Pydantic 的职责（`internal/schemas`）：

```go
// 相关性判定输出的结构化约束
type RelevanceVerdict struct {
    IsRelevant bool     `json:"is_relevant"` // 是否与互联网/编程/AI 相关
    Confidence float64  `json:"confidence"`  // 置信度 0~1，低于阈值进入人工复核
    Category   Category `json:"category"`    // 所属分类
    Reason     string   `json:"reason"`      // 可解释的判据
}
```

- 所有 LLM 输出都通过 `model.Client.CompleteJSON` 反序列化到对应结构体。
- 解析失败 → 重试 → 简化输出 → 人工介入（三级降级）。
- `Confidence` 低于阈值 → 进入人工审核队列，而非直接推送。

### 4.4 Prompt 管理

从「写 Prompt」升级为「管理 Prompt」（阶段一第 3 点）：

- **Prompt 是资产**：独立管理（`internal/prompt`），版本化、可回滚。
- **职责分离**：System Prompt 定义行为边界，User Prompt 携带具体任务，Few-shot 示例沉淀在 Prompt 内。
- **注入防护**：GitHub 项目描述 / README 属于「不可信输入」，需与指令做边界隔离。

### 4.5 记忆层（Memory）

- **去重记忆**：已处理项目的 `repo_id` 持久化，避免重复推送（幂等）。
- **偏好记忆**：记录用户兴趣标签，反向优化相关性判断的阈值与类别权重。
- **会话记忆**：单次任务内的中间状态（如本轮已抓取的列表）。

### 4.6 知识层（RAG，阶段二）

GitPulse 的 RAG 场景：**历史摘要 + 用户偏好** 沉淀为知识库，在判断「这个项目是否值得推」时检索历史相似项目，实现「之前推过类似的，这次可以合并/跳过」。这也是「多路召回 + Rerank」的练习场。

### 4.7 推送层

- **Adapter 模式**：`WeChatAdapter` / `EmailAdapter` / `DingTalkAdapter` / `SlackAdapter`，统一 `Send(ctx, Message)` 接口（`internal/push`）。
- **失败重试**：指数退避；**最终一致性**：推送结果落库，可对账。
- **频率控制**：用户可配置推送频率与免打扰时段（治理的一部分）。

## 5. 技术选型

> 选型原则：**先用最主流、最成熟的方案，把「工程化能力」练扎实，再谈替代方案。**

| 模块 | 首选方案 | 备选 / 演进 | 说明 |
|---|---|---|---|
| **语言** | Go 1.22+ | — | 强类型、编译期校验、单二进制部署，契合「稳定可控」 |
| **模型** | DeepSeek（OpenAI 兼容 API） | 分层路由：mini 模型做分类，大模型做摘要 | 成本可控是关键 |
| **Agent 框架** | **手写循环**（不引入重框架） | 可选接 OpenAI 兼容 Go SDK | Go 生态无 LangGraph 等价物，手写循环反而更契合学习「本质」 |
| **结构化输出** | Go `struct` + `encoding/json` | `invopop/jsonschema` 生成 JSON Schema | 编译期类型安全 |
| **GitHub 数据** | `google/go-github` | 手写 REST client（阶段一可先用 stdlib `net/http`） | 注意限流 |
| **向量库（RAG）** | Qdrant / Weaviate | pgvector / Milvus | 阶段二引入 |
| **可观测性** | OpenTelemetry Go SDK + `log/slog` | Langfuse / LangSmith（经 OTLP 导出） | 阶段五引入 |
| **调度** | `robfig/cron`（进程内） | K8s CronJob / GitHub Actions | 从本地到生产 |
| **存储** | SQLite（`modernc.org/sqlite`，纯 Go 无 CGO） | PostgreSQL + Redis | 去重、偏好、审计日志 |
| **配置** | `os.Getenv` + `.env` | `caarlos0/env` / `koanf` | 密钥不入库 |
| **部署** | Docker Compose | Kubernetes | 阶段五 |
| **包管理** | Go Modules（`go mod`） | — | 可复现构建 |

## 7. 学习路线与里程碑对照

`learn/learn.md` 的五个阶段，在本项目中都有对应的落地里程碑：

| 阶段 | 学习内容 | GitPulse 里程碑 | 完成标志 |
|---|---|---|---|
| **一、基础认知与单 Agent** | LLM API、结构化输出、Function Calling、Prompt 管理 | **M1**：跑通单 Agent 闭环 | 能自动完成「采集→分类→摘要→推送」全流程，输出结构化、可解析 |
| **二、企业级 RAG** | RAG Pipeline、多路召回、Rerank、语义治理 | **M2**：引入历史摘要知识库 | 判断时能检索历史项目，实现相似项目合并/去重，提升推送质量 |
| **三、架构与多 Agent 编排** | DAG Plan&Execute、上下文工程、分层路由 | **M3**：编排升级 | 低置信度分支、失败重试、人工审核队列等需要编排的场景落地 |
| **四、MCP 与企业集成** | MCP、工具白名单、权限边界 | **M4**：MCP 化 | 将核心能力暴露为 MCP Server，可被任意 Agent 调用 |
| **五、工程化与治理** | 可靠性、可观测性、成本、Eval、治理、部署 | **M5**：生产可信 | 有完整 trace / Eval / 告警 / Docker&K8s 部署 / 审计 |

**里程碑推进原则**：每个里程碑都必须「可运行 + 有测试 + 可观测」，而不是「写完了但没验证过」。企业级的核心是**证据**，不是代码堆砌。

## 8. 企业级能力清单

这是从「能跑」到「生产可信」的硬性清单，也是 GitPulse 区别于普通个人项目的关键。每一项都可作为独立的验收点。

### 8.1 稳定（Reliability）

- [ ] 指数退避重试（1s → 2s → 4s），避免对 GitHub API / LLM API 造成雪崩
- [ ] 结构化输出解析失败的三级降级（重试 → 简化 → 人工）
- [ ] 工具调用超时与熔断
- [ ] 任一步骤失败不影响整体（失败降级为跳过并告警）

### 8.2 可控（Controllability）

- [ ] 分层模型路由：分类用 mini 模型，摘要用大模型（成本 17 倍差异）
- [ ] Token 消耗按「步骤 / Agent / 工具」归因
- [ ] 高频结果缓存、Prompt 去重压缩

### 8.3 可观测（Observability）

- [ ] 全链路 trace：每次 PLAN/ACT/OBSERVE 都有轨迹
- [ ] 关键指标：工具调用成功率、平均延迟、Token 分布、重试率、人工介入率
- [ ] 告警：失败率 / 成本超阈值时主动通知

### 8.4 可治理（Governance）

- [ ] Prompt 版本管理（可追溯、可回滚）
- [ ] Agent 身份与审计日志（谁、何时、做了什么）
- [ ] 工具白名单与分级权限
- [ ] 高风险动作（如向用户推送）支持人工复核节点
- [ ] 评估体系（Eval）：批量化、可重复，每次变更后回归对比

## 9. 开发规范与约定

- **语言与注释**：中文文档、英文代码；Go doc 注释遵循「注释以标识符开头」约定，说明「为什么」而非「是什么」。
- **类型与校验**：所有外部数据（GitHub 返回、LLM 输出）进入系统即校验（反序列化到 `internal/schemas` 结构体）。
- **密钥管理**：所有密钥经 `.env` / 环境变量注入，`.env` 不入库（`.gitignore`）。
- **提交规范**：一个 commit 只做一件事，提交信息用「动词开头」的祈使句（如 `feat: add relevance judge tool`）。
- **测试门槛**：核心逻辑（去重、阈值判断、降级策略）必须有单测；合入前 `go test ./...` 全量通过。
- **代码风格**：提交前 `gofmt` + `go vet` 干净；导出标识符必须有 doc 注释。
- **可复现构建**：依赖锁定（`go.sum` 入库），Docker 镜像可复现。
- **优先可观测**：新增一个工具 / 步骤，同时就补上对应的 trace 埋点与日志，不「事后补」。

## 11. 未来演进路线

- **M1 → M5**：按第 7 节的里程碑推进，逐步补齐企业级能力。
- **多 Agent 化**：当出现「风险检测 + 合规审查 + 通知」等并发场景时，引入事件驱动并发（阶段三）。
- **MCP 化**：将 GitPulse 的核心能力（GitHub 监控、相关性判断、摘要）暴露为 MCP Server，成为其他 Agent 的基础设施（阶段四）。
- **平台化**：从「定时推送给自己」演进为「可配置订阅服务」，支持多用户、多兴趣领域（治理与多租户）。
- **云原生部署**：迁移到 K8s + 消息队列 + Serverless 推理，与后端基础设施（API 网关、监控体系）集成。
